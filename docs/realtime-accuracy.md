# 실시간 데이터 정확도 측정 (2026-10-08 10:39–10:46 KST)

## 측정 방법
- **위치 API(realtimePosition)**: 배포된 사이트(https://pyw31337.github.io/metro/)를 헤드리스 크롬으로 7분 동안 열어 두고, 앱이 실제로 받은 응답(공개 프록시 cors.eu.org 경유)을 그대로 기록. 노선 20개, 응답 46건, 열차 기록 1,402건.
- **도착 API(realtimeStationArrival)**: 같은 사이트가 종착역 15곳을 조회한 응답 + 공개 sample 키로 서울역을 15초마다 22회 조회(110건). sample 키는 한 번에 5건만 줘서 다른 역은 이 방법으로 볼 수 없음.
- 지연(lag) = 응답을 받은 시각 − 응답 안의 데이터 생성 시각(recptnDt).
- 앱은 노선을 돌아가며 조회해서, 한 노선을 다시 조회하기까지 보통 25–70초 걸림.

## 추론 (측정이 아니라 해석)
- 위치 API 정보는 **보통 1–1.5분 늦게 도착**한다. 역 사이 주행은 1.5–2.5분이라, 화면의 열차는 대부분 "마지막 보고 이후를 추정한 위치"일 수밖에 없다.
- 새 모델로 캡처 데이터를 다시 돌린 결과:
  - 보고 위치에서 30m 넘게 진행시킨 열차가 대부분이다.
  - 다음 보고가 왔을 때 69%는 이미 '다음 역에서 대기' 상태였다(다음 역을 넘지 않도록 막았기 때문).
  - 새 보고로 고쳐지는 거리는 중앙값 370m, 상위 10%는 1.1km 이상이다.
  - 이 보정은 선을 따라 이동하거나(가까우면) 바로 옮겨지며, 선 밖으로 나가지는 않는다.
- barvlDt 한 건을 대조한 결과(4호선 4556: '전역 도착' 120초 → 실제 서울 도착 보고까지 약 110초)는 ±1분 정도로 맞았다. 표본이 1건이라 일반화할 수는 없다.
- 그래서 "몇 분 뒤 도착"은 도착 API의 남은 시간을 데이터 나이만큼 보정해서 보여 주는 편이 지도 애니메이션보다 믿을 만하다. 남은 시간이 없는 노선은 "약 n분(추정)"으로 표시한다.
